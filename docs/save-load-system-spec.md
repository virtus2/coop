# Save & Load 시스템 기획 명세 (Containment Breach)

유저님의 답변을 바탕으로 확립된 세이브/로드 시스템의 기획 및 구현 명세서입니다.

## 1. 세이브 데이터 구조 (Save Data Schema)

세이브 파일은 JSON 포맷으로 로컬(호스트)에 저장되며, 다음의 데이터를 포함합니다.

### 1.1 메타데이터 (Metadata)
- `Version`: 세이브 파일 버전 (업데이트 호환성 체크용)
- `Timestamp`: 저장된 시간
- `PlayTime`: 누적 플레이 시간

### 1.2 월드 및 게임 진행 상태 (World & Progression State)
- `CurrentWave`: 현재 웨이브 진행도
- `CoreHealth`: 중앙 격리 코어의 현재 체력/내구도
- `DefeatedBosses`: 처치 완료된 특급 격리 개체(보스) 목록
- `UnlockedSectors`: 개방된 연구 구역(Sector) 목록 및 전력 복구 상태

### 1.3 맵 및 오브젝트 상태 (Map & Object State)
- **맵 생성 데이터:**
  - `MapSeed`: 절차적 맵 생성에 사용된 난수 시드(Seed) 값
- **변경 사항 (Delta State):**
  - `DestroyedProps`: 해체/파괴된 기존 가구 및 환경 오브젝트들의 고유 식별자(ID) 리스트
  - `BuiltStructures`: 유저가 건설한 바리케이드, 터렛 등의 목록 (종류, 위치 좌표, 회전값, 현재 체력, 남은 탄약 등)
  - `DroppedItems`: 바닥에 떨어져 있는 아이템 목록 (아이템 식별자, 위치, 회전, 내구도). 
    - **최적화 룰:** 물리 부하 방지를 위해 필드 내 최대 500개(예시)로 보존 개수 제한. 초과 생성 시 가장 오래된 것부터 자동 소멸.
  - `OpenedDoors`: 수동으로 개방된 보안 문이나 잠금 해제된 캐비닛 상태

### 1.4 플레이어 데이터 (Player Data)
- **Key:** `SteamID` (또는 오프라인/에디터 테스트용 고유 GUID)
- **Value:**
  - `Position` & `Rotation`: 저장 당시의 월드 위치 및 방향
  - `Health`: 남은 체력
  - `IsDead`: 저장 당시 사망 여부
  - `Inventory`: 인벤토리 배열 (각 슬롯의 아이템 데이터, 내구도, 부착물 등)

## 2. 세이브/로드 프로세스

### 2.1 저장(Save) 프로세스
1. **발생 시점:** 매 웨이브 방어 성공 후 **정비 단계(Preparation Phase)** 진입 시마다 **자동 저장(Auto-Save)** 수행.
2. **조건 검사:** 전투 중이거나 보스전 등 예외 상황에서는 세이브 제한.
3. **데이터 직렬화 & 로컬 저장:** 호스트 PC 기준 특정 경로에 취합된 데이터를 파일로 저장.

### 2.2 불러오기(Load) 프로세스
1. **맵 재건(Reconstruction):** 세이브 파일의 `MapSeed`를 사용하여 빈 월드에 초기 맵을 절차적으로 똑같이 재작성합니다.
2. **델타 적용(Delta Apply):**
   - 맵 생성 시 부여된 고유 ID를 대조하여 `DestroyedProps`에 포함된 오브젝트는 즉시 삭제(Destroy)합니다.
   - `BuiltStructures`와 `DroppedItems`를 해당 위치에 스폰합니다. (물리 튕김 현상 방지를 위해 초기 생성 시 강제 Sleep 처리 적용)
3. **진행도 복구:** 웨이브 번호, 코어 체력, 구역 해금 상태를 세팅합니다.
4. **플레이어 접속:**
   - 호스트 및 클라이언트가 접속할 때마다 세이브 파일의 `SteamID`를 조회하여 인벤토리와 체력, 위치를 복원합니다.
   - ⚠️ **사망 처리:** 세이브 당시 `IsDead = true`였던 유저는 부활하지 않고 **관전 모드**로 로드되며, 다음 다가오는 웨이브를 클리어해야만 부활할 수 있습니다.
   - 신규 접속자(데이터 없음)라면 기본 스폰 지점에서 빈 인벤토리로 시작합니다.

## 3. 발생 가능한 핵심 예외 케이스 및 해결 방안

### ⚠️ 예외 1: 오브젝트 식별자 (ID) 불일치 문제
- **해결 방안:** 절차적 맵 생성 시, 스폰되는 오브젝트는 생성 인덱스와 좌표를 섞어 **고유 해시(Hash) ID를 강제로 발급**해야 델타 데이터를 정상 적용할 수 있습니다. (Unity의 InstanceID 사용 불가)

### ⚠️ 예외 2: 로드 시 플레이어 끼임 문제 (Wall Clipping)
- **해결 방안:** 플레이어 로드 위치가 유효한 `NavMesh` 범위 밖(벽 속 등)이라면, 가장 가까운 안전 지대나 중앙 코어 챔버로 위치를 자동 보정합니다.

### ⚠️ 예외 3: 드롭 아이템 폭발 현상 (Physics Explosion)
- **해결 방안:** 바닥 아이템들을 저장된 좁은 틈에 대량으로 동시 스폰하면 물리 엔진이 튕겨냅니다. 아이템 로드 직후 1~2초간 `IsKinematic`을 켜두거나 Sleep 상태로 고정시켜 안정화합니다.

### ⚠️ 예외 4: 오프라인 모드 및 에디터 테스트 시 SteamID 부재
- **해결 방안:** `PlatformService`를 두어 Steam 미연동 상태에서는 `SystemInfo.deviceUniqueIdentifier` 나 임의의 GUID를 fallback으로 사용하여 세이브 시스템을 테스트할 수 있도록 합니다.

### ⚠️ 예외 5: 게임 패치/업데이트 시 맵 생성 알고리즘 변경 (버전 호환성)
- **상황:** 게임 업데이트로 새로운 방이나 구조물이 추가되면, 동일한 Seed라도 다른 맵이 생성되어 델타(Delta) 데이터의 위치가 완전히 어긋나게 됩니다.
- **해결 방안:** 메타데이터의 `Version`을 대조하여, 맵 생성 알고리즘이 변경된 메이저/마이너 업데이트 이후에는 **구버전 세이브 파일을 '호환되지 않음(불러오기 불가)' 처리**하고 새 게임을 시작하도록 강제합니다. (개발 복잡도 대폭 하락)

### ⚠️ 예외 6: 세이브 파일 관리 구조 (다중 슬롯)
- **상황:** 호스트가 A라는 친구들과 플레이하다가, 내일 B라는 친구들과 처음부터 다시 플레이하고 싶을 수 있습니다.
- **해결 방안:** 세이브 파일은 단일 덮어쓰기가 아닌 **'방 이름' 또는 '슬롯(Slot 1,2,3...)' 기반의 다중 세이브 시스템**을 제공합니다. 메인 메뉴에서 방을 팔 때 로드할 세이브 파일을 선택할 수 있게 UI를 설계합니다.

### ⚠️ 예외 7: 웨이브 도중 난입(Hot-join)하는 신규 유저 처리
- **상황:** 방어 전투가 한창 진행 중일 때 새로운 친구가 방에 접속하는 경우.
- **해결 방안:** 어뷰징 방지 및 긴장감 유지를 위해, 전투 중 난입 시 즉시 스폰하지 않고 **관전 모드**로 대기시킵니다. 해당 웨이브가 종료되고 '정비 단계'가 되어 자동 저장이 트리거될 때 스폰하여 합류하게 합니다.

### ⚠️ 예외 8: 방어 구조물(건설 시스템) 최대 개수 제한
- **상황:** 바리케이드나 터렛을 맵 전체에 무제한으로 건설하면 세이브 용량 및 네트워크/물리 연산 부하가 심각해집니다.
- **해결 방안:** 최적화를 위해 월드 전체에 **최대 설치 가능한 구조물 개수 제한(예: 100~200개)**을 둡니다. 제한 도달 시 UI 경고 메세지를 띄워 더 이상 짓지 못하게 하고 낡은 방어막을 해체하도록 유도합니다.

### ⚠️ 예외 9: 게임 오버(패배) 시 세이브 데이터 처리
- **상황:** 코어가 파괴되어 방어에 실패하고 패배(Game Over) 화면이 출력되었을 때 기존 세이브의 취급.
- **해결 방안:** 하드코어 생존 룰을 적용하여, 패배 시 해당 방(세이브 슬롯)의 세이브 파일은 **즉시 영구 삭제**됩니다. 유저는 아무런 보상이나 메타 프로그레션 없이 100% 백지상태에서 새로운 게임을 시작해야 합니다.

### ⚠️ 예외 10: 스팀 클라우드(Steam Cloud) 연동 동기화
- **상황:** 유저가 PC방이나 다른 노트북에서 접속했을 때 기존에 진행하던 방을 계속 호스팅하고 싶은 경우.
- **해결 방안:** 스팀 클라우드 동기화를 지원하도록 세이브 경로를 구성합니다. 모든 세이브 파일은 `Application.persistentDataPath` 하위의 특정 폴더(`Saves/`)에 저장하여 스팀 클라이언트가 자동으로 업로드/다운로드할 수 있게 연동합니다.

## 4. 맵 생성 및 로비 진입 아키텍처

세이브/로드 기능이 완벽하게 작동하기 위한 맵 생성 및 로비(메인 메뉴)의 동작 구조입니다.

### 4.1 절차적 맵 생성 (Procedural Map Generation)
- **오픈 스페이스 그리드 배치:** 미로 형태가 아닌, 거대한 X * Y 오픈된 격자(Grid) 공간에 방(Room) 프리팹들을 섬처럼 흩뿌려 배치하는 방식을 사용합니다.
- **실시간 네비메시(NavMesh) 베이크:** 맵 배치가 완료된 직후, 코드를 통해 `NavMeshSurface.BuildNavMesh()`를 호출하여 몬스터가 길을 찾을 수 있도록 런타임에 네비메시를 굽습니다.

### 4.2 프롭 고유 ID 발급 기법
- 방 안에는 파괴/상호작용 가능한 가구(자판기, 캐비닛 등) 프리팹이 미리 배치되어 있습니다.
- 맵 생성기가 각 방을 배치할 때, 방 안에 있는 모든 프롭을 스캔하여 **`Room_{GridX}_{GridY}_Prop_{Index}`** 형태의 고유 ID문자열을 강제 발급합니다.
- 이렇게 부여된 고유 ID 덕분에, 방 프리팹 안에 가구를 미리 예쁘게 배치해두기만 해도 세이브/로드 시 "어떤 가구가 부서졌는지" 정확하게 추적하여 맵에서 삭제(Destroy)할 수 있습니다.

### 4.3 로비(Lobby) 진입 판단 로직 (새 게임 vs 이어하기)
게임 씬(Game Scene) 진입 시 맵을 처음부터 새로 팔지, 세이브를 불러올지 결정하는 로직은 전역 변수(Global Settings)를 통해 제어됩니다.

1. **메인 메뉴 UI 선택:**
   - **[새 게임]:** 랜덤 시드를 새로 뽑고, 전역 변수 `GlobalSettings.LoadSaveSlot`을 `null`로 설정한 뒤 게임 씬으로 넘어갑니다.
   - **[이어하기]:** 유저가 선택한 세이브 파일 이름을 `GlobalSettings.LoadSaveSlot`에 기록하고 넘어갑니다.
2. **게임 씬 부트스트랩 (GameSceneBootstrap):**
   - 씬이 시작되면 매니저가 전역 변수를 확인합니다.
   - **`null`일 경우:** 새 시드로 맵 생성기(`MapGenerator`)만 실행하고 끝냅니다.
   - **값이 있을 경우:** 저장된 파일의 시드(Seed)를 꺼내 맵 생성기를 똑같이 돌린 뒤, 세이브 매니저의 `ApplyDelta(SaveData)` 함수를 호출해 부서진 사물들을 지우고 유저가 지은 터렛과 바닥 아이템들을 스폰합니다.
